# Stage 3 brief: AMCOS member and delivery records

**Track:** .NET (ASP.NET Core) · **Mode:** 2, plan together and you write the core logic · **Time:** 3–6 months (estimate) · Read `house-rules.md` first.

## The problem
Farmers deliver their crop to a primary cooperative (AMCOS), which weighs and grades it and passes the figures on for payment. Officials have blamed late payments partly on wrong payment details, and members often cannot check what they delivered or what they were owed. The research report gives the sources and says plainly how thin some of them are.

## Goal
An ASP.NET Core application a cooperative could run: a clean member register, deliveries per member, a statement each farmer can check, and an export for the auditor. **It records what is owed and what was paid; payments themselves happen elsewhere.**

## Build
1. **Roles:** manager, clerk, auditor, member. Authorization policies decide what each can see and do. The web screens use cookie login; the API uses JWT bearer tokens.
2. **Member register:** membership number, name, phone number in one international format, and payment details (a bank account or a wallet). Payment details have a state: unverified, or verified by a second officer. Any change sets them back to unverified and is kept in a history.
3. **Seasons and grades:** seasons, crops, grades and collection points. The price per grade for a season is an input the manager sets.
4. **Deliveries:** the clerk records member, date, collection point, grade and weight, and the member gets a receipt number. Store weights as integers in a unit you state.
5. **Statements:** per member and season: deliveries, the value owed, payments recorded against it, and the balance.
6. **Auditor's export:** members, deliveries, payment records and every change to payment details, with who did what and when, as CSV. The auditor can read everything and change nothing.
7. **Offline capture:** a clerk at a collection point with no connection keeps recording deliveries, and they sync later. Each captured delivery carries an identifier made on the device, the sync endpoint is safe to call twice, and conflicts go to a review list for the manager.
8. **API:** a REST API for members, deliveries, statements and sync, with pagination, validation, problem-details errors and an OpenAPI document generated by the built-in support.
9. **One front end:** Blazor with static server rendering, or React on the API. Pick one and keep it light.
10. **Quality:** xUnit tests; integration tests with WebApplicationFactory against a real PostgreSQL in Testcontainers; analyzers with nullable warnings as errors; `dotnet format`; a GitHub Actions pipeline that runs all of them, fails on NuGet Audit warnings and builds the container image.
11. **Deployed** as a container.

## Edge cases you must handle
- The same batch of offline deliveries is synced twice.
- Two devices change the same record while offline.
- A clerk's login expires while offline: nothing captured is lost.
- A delivery for a member whose payment details are unverified: it is recorded, and the member is flagged on the payment list.
- Payment details are changed just before a payment list is produced.
- A grade price is corrected after deliveries were recorded against it.
- A weight of zero, or one far beyond anything a person could carry in.
- A member tries to open another member's statement; the auditor tries to change a record through the API.

## It works when
- [ ] Every role can do its own work and nothing else; integration tests prove each policy, for the screens and for the API.
- [ ] A member's balance always equals the value of their deliveries minus payments recorded; no delivery or payment record is ever edited or deleted.
- [ ] Syncing the same batch twice changes nothing the second time, shown by a test.
- [ ] Every change to payment details is in the history with who made it, and unverified details never appear on a payment list as ready.
- [ ] The OpenAPI document is generated from the code and matches what the API does.
- [ ] The build has zero warnings with nullable enabled, and the pipeline is green on the main branch.
- [ ] The app is live, and only invented members and accounts are in it.

## Know before real use
Members' payment details are personal data and a target for fraud; a real deployment brings Personal Data Protection Act duties. The tool is only worth something if a cooperative agrees to use it, so interview one before building further. Payments run through unions and government systems that this app does not touch.
