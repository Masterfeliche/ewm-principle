# Stage 5 brief: Month-end and share-out rush

**Track:** .NET (ASP.NET Core) · **Mode:** 2–3; Mode 4 only for skills you have proved · **Time:** ongoing (estimate) · Read `house-rules.md` first.

## The problem
Month-end contributions, loan repayments and the end-of-cycle share-out arrive together, for every group at once. A system that works for one group on a quiet day falls over, and the failures (a ledger that no longer balances, a contribution counted twice, a queue that never drains) are the expensive kind.

## Goal
Take your Stage 4 system, state a load target, test it, find what breaks, fix it, and write up what you learned. All traffic is generated by you against your own mock gateway and simulators.

## Build
1. **A target, written first.** For example: 500 groups, 300 ledger postings a second for 15 minutes, 95% of requests under 300 ms, no lost or doubled contribution, every group's trial balance at zero afterwards, queues drained within 5 minutes of the peak. The numbers are yours to choose and defend.
2. **Load scripts** in k6 or NBomber for the main journeys: record a meeting, receive a payment notification, view a member statement, run the month-end reports.
3. **A notification storm.** Replay thousands of duplicate and out-of-order notifications from your mock gateway during the load test.
4. **A posting race.** Many officers and workers posting to the same group's accounts at once; prove every journal entry balances and no account drifts.
5. **A share-out run** for many groups at the same time, checked to the shilling against your Stage 1 calculator.
6. **Tracing.** OpenTelemetry traces across web request, broker message, background worker and outbound call, so one slow posting can be followed end to end.
7. **Diagnostics.** Use `dotnet-counters` and `dotnet-trace` on the running system during the test, and say what each showed.
8. **Scale out.** Run at least two app instances and two workers behind a proxy. Find and remove anything that only worked because there was one process.
9. **Fixes.** For each bottleneck: the evidence, the change (an index, a query rewrite, a cache, more workers, connection pooling), and the measurement after.
10. **A performance report** (2–4 pages): the target, the setup, what broke first and why, each fix with before and after numbers, what you would do next, and what you could not test.

## Things to look for
- Queries that run once per row (N+1) on the statement and report screens.
- Missing indexes on tenant, date and reference columns.
- Database connections running out when instances and workers multiply.
- A cached item expiring for every instance at once, because stampede protection covers one instance only.
- Retries on outbound calls repeating a write.
- Workers stuck behind one slow simulator call.
- Blocking on async code (`.Result`) starving the thread pool.
- Memory and allocations growing in long-running workers.

## It works when
- [ ] The target is met, or the report says plainly which part is not and why.
- [ ] No contribution or ledger entry is lost or duplicated during the test, shown by a reconciliation run and a trial balance afterwards.
- [ ] Every fix has a before and after measurement; none is a guess.
- [ ] A single notification can be traced from the endpoint to the broker, the worker, the database and the SMS simulator.
- [ ] The system gives the same results with one instance and with several.
- [ ] The report states the machine sizes and what the test could not cover.

## Stretch change (transfer check): go regional
Add Kenya, Uganda and Rwanda without changing the core: each country's wallet notification format, data-protection rule, phone format and currency sits behind an interface or a setting. Look up the details that the research left unconfirmed (currency decimals, number lengths, interface languages) as part of the work. Sandboxes and mocks only.

## Rebuild from memory (a week later)
Without looking: write a load script for one journey with a ramp-up, a threshold and a check, and explain each number in it.
