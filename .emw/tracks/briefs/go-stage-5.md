# Stage 5 brief: Reconciliation under load

**Track:** Go · **Mode:** 2–3; Mode 4 only for skills you have proved · **Time:** ongoing (estimate) · Read `house-rules.md` first.

## The problem
At month end, sales, fee deadlines and payment callbacks arrive together. A reconciliation system that keeps up on a quiet day falls behind: the queue grows, the database runs out of connections, a worker's memory climbs until the platform kills it, and the report is hours late or wrong. These failures only show under load, and they are the expensive kind.

## Goal
Run your Stage 4 system on Kubernetes, state a load target, load-test it while your mock gateway storms it, find what breaks, fix it with evidence, and write up what you learned. All traffic is generated by you against your own services.

## Build
1. **A target, written first.** For example: 100 clients, 400 sales requests a second and 400 notifications a second for 15 minutes, 99% of ingest requests under 200 ms, no accepted event lost, queue lag back to zero within 5 minutes of the peak, every planted mismatch reported. Choose your own numbers and say why.
2. **Kubernetes.** Deploy every service to a cluster (a local one is enough): deployments with CPU and memory requests and limits, readiness probes, SIGTERM draining with a shutdown time shorter than the platform's grace period, configuration and secrets kept out of the images, and more than one replica of each stateless service.
3. **Load scripts** in k6 or vegeta for the main journeys: send sales in batches, receive notifications, read the report.
4. **A callback storm.** During the load test the mock gateway sends late, duplicate, out-of-order and missing callbacks at a set rate, with a fixed seed so the run can be repeated.
5. **Failures during load.** Do a rolling update in the middle of a run, and kill a worker pod in the middle of a run. Nothing accepted may be lost either time.
6. **Profiling.** Take CPU, heap and goroutine profiles under load from the internal port. For each bottleneck: the evidence, the change, and the measurement after.
7. **Runtime settings.** Check what GOMAXPROCS each container ends up with against its CPU limit; set and justify `GOMEMLIMIT`; show what happens to latency and memory when it is set wrongly.
8. **Profile-guided optimisation.** Build one service with a CPU profile collected under your load test, and measure the difference against the build without it. Report it even if the difference is small.
9. **Scaling.** Scale the API and the worker out and show where adding replicas stops helping (database connections, the queue, one hot table) and what you did about it.
10. **Dashboards.** Request rate, error rate and latency per service; queue lag; job failures; database connections in use; memory against the limit; goroutine count.
11. **A performance report** (2–4 pages): the target, the cluster and machine sizes, what broke first and why, each fix with before and after numbers, the settings you ended with, what you would do next, and what you could not test.

## Things to look for
- Replicas multiplying database connections past what PostgreSQL allows.
- Missing indexes on client, reference and time columns.
- One slow status query to the gateway holding up a whole worker.
- A consumer that falls behind and never catches up because every message does a full lookup.
- Memory growing in a worker under duplicates, and a container killed for it.
- CPU throttling from a limit that is too tight.
- Goroutines that pile up when the gateway stops answering.
- A duplicate check that is fast only while the cache is warm.
- Requests dropped during a rolling update because a pod took traffic before it was ready or after it began to stop.

## It works when
- [ ] The target is met, or the report says plainly which part is not and why.
- [ ] No accepted sale or notification is lost or counted twice during the test, the rolling update or the pod kill, shown by a reconciliation run afterwards against what the load script and the gateway say they sent.
- [ ] Every fix has a before and after measurement; none is a guess.
- [ ] One request can be traced from the load script's call to the queue, the worker, a job and the database.
- [ ] The race detector and the goroutine leak profile are clean on the build you tested.
- [ ] The report states the machine sizes, the cluster setup and what the test could not cover.

## Stretch change (transfer check)
Do one of these.

**Go regional.** Add Kenya, Uganda and Rwanda without changing the core: each country's notification format, status words, phone format and currency sits behind an interface or a setting, and the mock gateway can speak each format. Look up the details the research left unconfirmed (currency decimals, number lengths and prefixes, interface languages) as part of the work, and keep money exact in each currency's smallest unit.

**A rate limiter in front of the API.** Per-client limits that hold across all replicas, with clear answers to the client when it is limited, a stated rule for what happens when the shared store is down, and a load test showing one noisy client can no longer slow the others.

## Rebuild from memory (a week later)
Without looking: write a load script for one journey with a ramp-up, a threshold and a check, and explain each number in it. Then, from a profile you have not seen before (ask a peer for one, or use one from an earlier run), say what the top three entries mean and what you would try first.

## Know before real use
A load test proves what you tested on the machines you used, with invented data; say so in the report and do not quote its numbers as what a production system will do. Never run load against a service you do not own, including any provider's sandbox. Going regional for real means each country's own provider contracts, certification and data-protection rules; the research report lists them and marks what it could not confirm. See `resources/research/East Africa software problems for PHP projects.md`.
