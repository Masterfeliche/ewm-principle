# Stage 5 brief: End-of-month rush

**Track:** PHP (Laravel) · **Mode:** 2–3; Mode 4 only for skills you have proved · **Time:** ongoing (estimate) · Read `php-house-rules.md` first.

## The problem
Month-end sales, fee deadlines and payment callbacks arrive together. A system that works for one shop on a quiet day falls over, and the failures (lost receipts, double-counted payments, a queue that never drains) are the expensive kind.

## Goal
Take your Stage 4 system, state a load target, test it, find what breaks, fix it, and write up what you learned. All traffic is generated by you against your own mocks.

## Build
1. **A target, written first.** For example: 200 shops, 500 requests a second on the sale screen for 15 minutes, 95% of requests under 300 ms, no failed sales, queue drained within 5 minutes of the peak.
2. **Load scripts** in k6 for the main journeys: record a sale, take a payment, issue a receipt, view the daily report.
3. **A webhook storm.** Replay thousands of duplicate and out-of-order callbacks from your mock gateway during the load test.
4. **A receipt race.** Many tills per shop issuing receipts at once; prove no number is skipped or repeated.
5. **Tracing.** OpenTelemetry traces across web request, queue job and outbound call, so one slow sale can be followed end to end.
6. **Octane.** Run the app on Octane with FrankenPHP. Find and fix any state that leaks between requests. Set a worker request limit and say why.
7. **Fixes.** For each bottleneck: the evidence, the change (an index, a cache, a query rewrite, more workers, connection pooling), and the measurement after.
8. **A performance report** (2–4 pages): the target, the setup, what broke first and why, each fix with before and after numbers, what you would do next, and what you could not test.

## Things to look for
- Queries that run once per row (N+1) on the report screens.
- Missing indexes on tenant, date and reference columns.
- Database connections running out when workers multiply.
- A cache that hides a slow query until it expires for everyone at once.
- Queue workers stuck on one slow provider call.
- Memory growing in long-running workers.

## It works when
- [ ] The target is met, or the report says plainly which part is not and why.
- [ ] No sale, payment or receipt is lost or duplicated during the test, shown by a reconciliation run afterwards.
- [ ] Every fix has a before and after measurement; none is a guess.
- [ ] A single request can be traced from browser to database to queue to mock provider.
- [ ] The report states the machine sizes and what the test could not cover.

## Stretch change (transfer check): go regional
Add Kenya, Uganda and Rwanda without changing the core: each country's wallet API, tax receipt system, data-protection rule, phone format and currency sits behind an interface or a setting. Look up the details that the research left unconfirmed (currency decimals, number lengths, interface languages) as part of the work.

## Rebuild from memory (a week later)
Without looking: write a k6 script for one journey with a ramp-up, a threshold and a check, and explain each number in it.

## Evidence to record
Items for `laravel.octane`, `laravel.scaling`, `php.performance`, `core.load-testing`, `core.caching-queues`, `core.observability` and `core.sql`. Present the performance report to an experienced developer and answer their questions; mark that item `verified_by: human`. Teaching it is the M4 evidence.
