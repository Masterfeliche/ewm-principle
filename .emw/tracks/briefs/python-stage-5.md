# Stage 5 brief: Load test and message understanding with evaluation

**Track:** Python (FastAPI, Celery and an AI specialism) · **Mode:** 2–3; Mode 4 only for skills you have proved · **Time:** ongoing (estimate) · Read `house-rules.md` first.

## The problem
Two things remain. First, the Stage 4 pipeline has only seen quiet days; at month-end, notifications arrive in a storm and the expensive failures appear (a queue that never drains, connections running out, payments counted twice). Second, your Stage 1 parser only reads the message shapes you wrote rules for. Real messages come in Kiswahili and English, change wording without notice, and are forwarded with extra text around them. A language model can read them, but a feature that "seems to work" on five examples is not a feature anyone should trust with money records.

## Goal
Part A: state a load target for the Stage 4 pipeline, test it, fix what breaks, and write it up. Part B: add a message-understanding feature backed by a language model, and prove how good it is with an evaluation suite built from your Stage 1 labelled samples. All traffic is generated by you against your own mocks, and **no real personal data is sent to any external model**.

## Build: Part A, load and performance
1. **A target, written first.** For example: a stated number of notifications a second for 15 minutes, 95% of ingest requests under a stated time, every payment matched within a stated delay, queue drained within 5 minutes of the peak, nothing lost or duplicated. Choose the numbers and say why.
2. **Load scripts** in Locust for the main journeys: create an order, receive a notification, query a payment's status, read the reconciliation report.
3. **A notification storm.** During the load test, have your mock gateway replay thousands of duplicate and out-of-order notifications.
4. **Profiling.** Attach py-spy to a web process and a worker under load. Find where the time goes before changing anything.
5. **Concurrency, measured.** Take one CPU-bound step (for example parsing or reconciliation) and one I/O-bound step. Measure each under asyncio, threads and processes, and explain the results in terms of the GIL. Optional: repeat the CPU-bound case on a free-threaded build and report what you found, including whether any dependency turned the GIL back on.
6. **Fixes.** For each bottleneck: the evidence, the change (an index, a cache, a query rewrite, a different worker count or kind, pool sizes), and the measurement after.
7. **A performance report** (2–4 pages): the target, the setup and machine sizes, what broke first and why, each fix with before and after numbers, what you would do next, and what you could not test.

## Build: Part B, message understanding
1. **The feature.** Given one free-text transaction message in Kiswahili or English, return amount (whole shillings), direction (in or out), counterparty and reference, or say that the text is not a transaction. Use one LLM provider's Python SDK; the output is validated against a Pydantic schema before anything else sees it.
2. **Where it sits.** In the order desk, a seller pastes a buyer's message as payment proof; the extraction fills in the proof's details for matching. An extraction is a suggestion: a match made from it is marked as such, low-confidence results wait for a person, and any mistake is fixed by a correcting record.
3. **The evaluation set.** Grow your Stage 1 labelled samples into a set large enough to mean something, covering both languages, every shape you know, non-transactions and awkward cases. Set part of it aside and never tune on that part. State the size and the mix in the README.
4. **The evaluation suite.** One command that runs the set and reports accuracy **per field**, per language, the rate of valid output, and cost and latency per message. Run the same set through your Stage 1 rule-based parser so there is a baseline to beat.
5. **A regression gate in CI.** The pipeline fails if any field's accuracy drops below the committed baseline. Decide and document whether CI calls the model live or replays recorded responses, and when the live run happens.
6. **A rule-based fallback.** When the model is unreachable, slow, over budget, or returns output that fails validation, the Stage 1 parser answers instead, and the result records which path produced it.
7. **Privacy.** A masking step removes names and phone numbers before any text leaves your system, with its own tests. The evaluation set contains only invented or anonymised messages. Nothing sent to the model, and nothing it returns, is logged with personal data.
8. **Checks on the model's answer.** An amount or reference that does not appear in the message is rejected. Text inside a message that reads like an instruction is treated as data, and you have test messages that try it.
9. **Limits.** A timeout, a retry rule, a spending cap per day, and calls made from a task, never from inside a request that a user is waiting on without a timeout. Pin the SDK version and keep it under the same locked install and audit as everything else.
10. **An evaluation report** (1–2 pages): the set, the results table for the model and the baseline, the errors grouped by kind, cost and latency, and what the feature should not be used for.

## Things to look for
- Database connections running out when workers multiply.
- Tasks stuck behind one slow outbound call.
- An async endpoint that blocks the event loop with a synchronous call.
- A cache that hides a slow query until it expires for everyone at once.
- Memory growing in long-running workers.
- Accuracy that looks high overall while one field, or one language, is poor.
- A prompt change that improves the examples you were looking at and makes the held-out part worse.
- Amounts that differ from the message by a factor of ten or a thousand (`15,000` against `15.000`).

## It works when
- [ ] The load target is met, or the report says plainly which part is not and why.
- [ ] No payment is lost or duplicated during the test, shown by a reconciliation run afterwards.
- [ ] Every fix has a before and after measurement; none is a guess.
- [ ] The concurrency experiment has numbers and an explanation you can defend.
- [ ] The evaluation command prints accuracy per field and per language, cost and latency, for the model and for the rule-based baseline.
- [ ] CI fails when you deliberately make a prompt worse.
- [ ] With the model switched off, the feature still answers through the fallback and says so.
- [ ] A test proves no unmasked name or phone number reaches the SDK call.
- [ ] Every extracted amount is a whole number of shillings that appears in the message.
- [ ] Both reports state what the tests could not cover.

## Know before real use
Transaction messages are personal data, and the research report lists financial transaction data as sensitive and says sending personal data abroad needs a permit. A hosted language model is an external party, usually abroad. Real use therefore needs legal advice and data-protection registration, not only a masking step. See the report named in `house-rules.md`; it is not legal advice.
