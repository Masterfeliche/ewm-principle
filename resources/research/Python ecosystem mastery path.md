# Modern Python pays learners who deploy

In late 2026, Python is the largest and best-paid of the three backend ecosystems compared in this series. Its demand, though, is pulled as much by AI and data work as by classic web backends. **Python 3.15 shipped on 9 October 2026** with explicit lazy imports, `frozendict` and UTF-8 by default. **Python 3.14 (October 2025) made the free-threaded, no-GIL build officially supported** ([devguide versions](https://devguide.python.org/versions/); [What's New 3.15](https://docs.python.org/3.15/whatsnew/3.15.html); [What's New 3.14](https://docs.python.org/3/whatsnew/3.14.html)). The everyday stack has consolidated quickly. uv and Ruff, Astral's Rust tools, now handle installs, locking, linting and formatting, and OpenAI agreed to buy Astral in March 2026 ([OpenAI](https://openai.com/index/openai-to-acquire-astral)). Django 6.x and FastAPI are the two frameworks to know, with SQLAlchemy 2.1, Pydantic v2, Celery and Gunicorn or Uvicorn around them. Python tops TIOBE at **20.86%**, is used by **57.9% of Stack Overflow's 2025 respondents and 71.8% of people learning to code**, and appears in **6,461 UK permanent job ads at a £71,991 median**. That is about 1.9x C#'s ad count and 14x PHP's, with medians £9.5k and £22k higher ([TIOBE](https://www.tiobe.com/tiobe-index/); [Stack Overflow 2025](https://survey.stackoverflow.co/2025/technology); [ITJobsWatch Python](https://www.itjobswatch.co.uk/jobs/uk/python.do)). The catch is that **AI appears in 38.7% of UK Python ads while Django and FastAPI together appear in under 7%**, and the entry level is the most crowded of any language. The best path for a newcomer has five stages: modern Python with types and tests, Django with SQL, a FastAPI service that is containerised and run in CI, production operation (queues, caching, observability, cloud), and finally scale and a chosen specialism. Each stage should end in a deployed artefact, because Python employers advertise for SQL, cloud and CI/CD far more often than for any framework.

## Python 3.15 leads a five-year support window

CPython follows PEP 602. A new minor version ships every October, gets about 18 months of bugfix releases, and then receives security fixes until five years after release ([PEP 602](https://peps.python.org/pep-0602/)). A proposal to switch to calendar version numbers such as "3.26" was rejected, so 3.16 follows 3.15 ([PEP 2026](https://peps.python.org/pep-2026/)). The table shows status on 20 November 2026.

| Version | Released | Status | End of life |
|---|---|---|---|
| 3.9 | Oct 2020 | End of life | 31 Oct 2025 |
| 3.10 | Oct 2021 | End of life | **1 Oct 2026** |
| 3.11 | 24 Oct 2022 | Security only | Oct 2027 |
| 3.12 | 2 Oct 2023 | Security only | Oct 2028 |
| 3.13 | 7 Oct 2024 | Security only | Oct 2029 |
| 3.14 | 7 Oct 2025 | Bugfix | Oct 2030 |
| 3.15 | **9 Oct 2026** | Bugfix (newest) | Oct 2031 |
| 3.16 | due 6 Oct 2027 | In development | Oct 2032 |

Source: [CPython devguide](https://devguide.python.org/versions/).

**A learner should install 3.14 or 3.15 and treat 3.12 as the floor.** The libraries set that floor, not the core team: **Django 6.1 and NumPy 2.5 require Python 3.12+, and FastAPI, SQLAlchemy 2.1 and pandas 3 require 3.11+** ([PyPI Django](https://pypi.org/project/Django/); [PyPI numpy](https://pypi.org/project/numpy/); [PyPI fastapi](https://pypi.org/project/fastapi/); [PyPI SQLAlchemy](https://pypi.org/project/SQLAlchemy/); [pandas 3.0](https://pandas.pydata.org/community/blog/pandas-3.0.html)). Production lags well behind the release table. In the PSF/JetBrains survey, collected in late 2024, 3.12 led at 35%, 3.11 had 21% and 3.10 had 15%, and **4% of respondents still used Python 2** ([JetBrains Python Developers Survey 2024](https://lp.jetbrains.com/python-developers-survey-2024/)). Servers running 3.10, now unsupported, will keep producing upgrade work for years.

### Modern Python is typed, lazy and safer by default

The Python a beginner meets now differs sharply from pre-2023 tutorials. Type hints grew in steps. Protocols and TypedDict arrived in 3.8 and the `X | Y` union syntax in 3.10 ([PEP 544](https://peps.python.org/pep-0544/); [PEP 604](https://peps.python.org/pep-0604/)). **PEP 695 in 3.12 replaced TypeVar boilerplate** with `def f[T](x: T) -> T` and a `type Alias = ...` statement ([PEP 695](https://peps.python.org/pep-0695/)). **3.14 made annotations lazy (PEP 649/749)**, so forward references no longer need quotes or `from __future__ import annotations` ([What's New 3.14](https://docs.python.org/3/whatsnew/3.14.html)). Structural pattern matching (`match`/`case`, 3.10) and dataclasses with `slots=True` and `kw_only` are everyday tools ([PEP 634](https://peps.python.org/pep-0634/); [dataclasses](https://docs.python.org/3/library/dataclasses.html)). 3.11 added `asyncio.TaskGroup` and exception groups with `except*`, which gave asyncio structured concurrency ([What's New 3.11](https://docs.python.org/3/whatsnew/3.11.html)).

Two recent features matter most for backend work. **Template strings (`t'...'`, PEP 750, 3.14)** evaluate to a `Template` object rather than a string, so a library can inspect the interpolated values before rendering. That is the foundation for injection-safe SQL and HTML building. **Explicit lazy imports (`lazy import json`, PEP 810, 3.15)** defer module loading until first use, which shortens startup for CLIs and services ([What's New 3.14](https://docs.python.org/3/whatsnew/3.14.html); [What's New 3.15](https://docs.python.org/3.15/whatsnew/3.15.html)). 3.15 also adds a built-in immutable `frozendict` (PEP 814), a `sentinel` type (PEP 661) and unpacking in comprehensions (PEP 798). It makes **UTF-8 the default text encoding regardless of locale** (PEP 686), which ends a whole class of Windows bugs ([What's New 3.15](https://docs.python.org/3.15/whatsnew/3.15.html)). Developer experience has improved too: keyword-typo suggestions and a syntax-highlighted REPL arrived in 3.14, and 3.15 adds hints for other languages' method names (`push` → `append`). 3.14 also added `pdb -p PID` to attach to a running process, and 3.15 added **"Tachyon", a sampling profiler that attaches to live processes** ([What's New 3.14](https://docs.python.org/3/whatsnew/3.14.html); [What's New 3.15](https://docs.python.org/3.15/whatsnew/3.15.html)).

### Free-threading is supported, but processes still scale web apps

Python's performance story changed more in 2025–26 than in the previous decade, but it has not changed how a typical web app scales. **PEP 779 made the free-threaded build "officially supported" in 3.14.** It remains a separate build, not the default, with no date set for the next phase ([PEP 779](https://peps.python.org/pep-0779/)). The current HOWTO puts its single-threaded cost at about 1% on macOS ARM and about 8% on x86-64 Linux. One caveat is critical: **importing any C extension not marked compatible silently re-enables the GIL** ([free-threading HOWTO](https://docs.python.org/3/howto/free-threading-python.html)). 3.14 also exposed subinterpreters to Python code through `concurrent.interpreters` and `InterpreterPoolExecutor` ([What's New 3.14](https://docs.python.org/3/whatsnew/3.14.html)). The JIT has had a rockier history. In July 2025, after 30 months of work, it was often slower than the interpreter ([DevClass](https://www.devclass.com/development/2025/07/09/despite-30-months-work-core-developer-says-pythons-jit-compiler-is-often-slower-than-the-interpreter/1629293)). That came two months after Microsoft ended its Faster CPython funding and laid off most of the team, which then continued as a community project ([discuss.python.org](https://discuss.python.org/t/community-stewardship-of-faster-cpython/92153)). By 3.15 the JIT had recovered to **roughly 7–8% faster on x86-64 Linux and 11–12% on ARM macOS**, but it is still experimental and off by default ([Phoronix](https://phoronix.com/news/Python-3.15-Released); [Python blog](https://blog.python.org/2026/03/jit-on-track/)). A draft PEP targets at least 20% from JIT plus free-threading by 3.17 ([PEP 836](https://peps.python.org/pep-0836/)).

The practical conclusion is plain. **Use asyncio for I/O concurrency and multiple processes for CPU parallelism**, and treat free-threading as something to pilot for CPU-parallel workloads with audited dependencies. Neither the JIT nor no-GIL is yet a reason to pick Python for CPU-bound services. When Python is the bottleneck, the ecosystem's answer is native code, usually Rust through PyO3, as in pydantic-core, Ruff and Polars.

## Astral's Rust tools became the default toolchain, then OpenAI bought them

The biggest shift in Python's daily experience came from outside CPython. **uv** installs Python itself (`uv python install`), creates projects, resolves and locks dependencies (`uv.lock`), and runs tools (`uvx`) in a single fast binary. **Ruff** replaces Flake8, isort and Black with one linter and formatter ([uv docs](https://docs.astral.sh/uv/); [Ruff docs](https://docs.astral.sh/ruff/)). uv was **the most admired technology in Stack Overflow's 2025 survey**, with 9.5% usage across all respondents ([Stack Overflow 2025](https://survey.stackoverflow.co/2025/technology)). That growth came after the last PSF survey. Its late-2024 data still showed pip at 74% for dependency management, Poetry at 20% and uv at only 12% ([JetBrains survey 2024](https://lp.jetbrains.com/python-developers-survey-2024/)). Astral's type checker **ty** has been in beta since December 2025 and was still on 0.0.x versions in October 2026, so mypy and pyright (which powers Pylance in VS Code) remain the production choices ([Astral blog](https://astral.sh/blog/ty); [PyPI ty](https://pypi.org/project/ty/)).

**On 19 March 2026 OpenAI announced it would acquire Astral**, folding the team into Codex and promising continued open-source support ([OpenAI](https://openai.com/index/openai-to-acquire-astral); [Simon Willison](https://simonwillison.net/2026/mar/19/openai-acquiring-astral/)). The tools are MIT/Apache-2.0 licensed, so they can be forked. Even so, teams standardising on uv now depend on a single AI vendor's goodwill, a governance question that .NET learners face with Microsoft and PHP learners do not. Lock files are converging slowly. PEP 751 standardised `pylock.toml`, but pip's `pip lock` is still experimental and uv reads and writes the format only behind preview flags, so `uv.lock` remains the working standard ([PEP 751](https://peps.python.org/pep-0751/); [discuss.python.org](https://discuss.python.org/t/community-adoption-of-pylock-toml-pep-751/89778)). In editors, VS Code leads with 48% against PyCharm's 25% ([JetBrains survey 2024](https://lp.jetbrains.com/python-developers-survey-2024/)). PyCharm merged its Community and Professional editions into one product with a free core tier ([JetBrains blog](https://blog.jetbrains.com/pycharm/2025/04/unified-pycharm/)).

The learner's quality stack therefore looks like this: uv, then Ruff, then pyright or mypy, then pytest with Hypothesis and coverage.py, then pre-commit, with tox or nox for multi-version testing ([pytest](https://docs.pytest.org/); [Hypothesis](https://hypothesis.readthedocs.io/); [pre-commit](https://pre-commit.com/)). Copied into GitHub Actions from the first project onward, that becomes the CI pipeline:

1. `uv sync --locked`
2. `ruff check` and `ruff format --check`
3. A type check
4. `pytest` with coverage
5. `pip-audit` against vulnerability databases ([pip-audit](https://github.com/pypa/pip-audit))
6. A Docker image build

### Supply-chain attacks are now a backend skill, not a footnote

PyPI has done much of what the platform can. **Trusted Publishing** uses OIDC to replace long-lived API tokens, and **PEP 740 attestations** can be verified against Sigstore transparency logs ([PyPI attestations](https://docs.pypi.org/attestations/security-model/)). The incidents keep coming anyway. The December 2024 ultralytics compromise could be audited precisely because of attestations ([PyPI blog](https://blog.pypi.org/posts/2024-12-11-ultralytics-attack-analysis/)). In September 2025 a malicious GitHub Actions workflow tried to steal PyPI tokens ([PyPI blog](https://blog.pypi.org/posts/2025-09-16-github-actions-token-exfiltration/)). In **April 2026, releases of litellm and telnyx shipped credential-harvesting malware** after a token leaked through a compromised Trivy dependency. PyPI noted that malware injected into widely used packages is a different threat from typosquatting ([PyPI incident report](https://blog.pypi.org/posts/2026-04-02-incident-report-litellm-telnyx-supply-chain-attack/)). The litellm case lands squarely on the AI-backend stack many Python learners will build on. Locking with hashes, auditing in CI, Trusted Publishing and treating CI tokens as secrets belong in stage 3 of any path, not in a late security module.

## Django and FastAPI split Python's backend between product and API work

Python has no single dominant web framework the way PHP has Laravel or .NET has ASP.NET Core. The three leaders are close. In the PSF/JetBrains survey (late-2024 data), **FastAPI reached 38%, up from 29% the year before and 21% in 2021, ahead of Django at 35% and Flask at 34%** ([JetBrains State of Python 2025](https://blog.jetbrains.com/pycharm/2025/08/the-state-of-python-2025/)). Stack Overflow 2025 shows the same order among all developers: FastAPI 14.8%, Flask 14.4%, Django 12.6% ([Stack Overflow 2025](https://survey.stackoverflow.co/2025/technology/)). The frameworks overlap rather than compete: **28% of Django developers also use FastAPI** ([DSF survey](https://www.djangoproject.com/weblog/2025/oct/31/django-developers-survey-2025-results/)).

**Django** is the batteries-included, long-support choice. The current release is 6.1.3. 5.2 LTS is supported until April 2028, and **6.2 LTS is due in April 2027** with support until April 2030. After that, Django switches to year-named versions, starting with "2028" in January 2028 ([Django download](https://www.djangoproject.com/download/)). Recent releases keep absorbing third-party packages. **Django 6.0 (December 2025) added a built-in Tasks framework, template partials suited to HTMX, and Content Security Policy support.** The Tasks framework ships no production worker yet, which drew criticism ([Django 6.0 release notes](https://docs.djangoproject.com/en/6.0/releases/6.0/); [InfoQ](https://infoq.com/news/2026/01/django-6-release)). **Django 6.1 (August 2026) added ORM fetch modes**: `FETCH_PEERS` loads a missing field for every instance in a queryset at once, which blunts N+1 queries. It also added database-level `on_delete` and raised PBKDF2 to 1.5 million iterations ([Django 6.1 released](https://djangoproject.com/weblog/2026/aug/05/django-61-released)). For APIs, Django REST Framework (3.18) still dominates existing code. **Django Ninja (1.8)** brings FastAPI-style type hints, Pydantic and automatic OpenAPI to Django ([PyPI djangorestframework](https://pypi.org/project/djangorestframework/); [PyPI django-ninja](https://pypi.org/project/django-ninja/)).

**FastAPI** is the API and AI-serving choice, and it carries more version risk. Version 0.165.0 shipped on 18 November 2026. It is **still pre-1.0, released very frequently, and lists many entries marked "Breaking Changes" in October–November 2026 alone** ([PyPI fastapi](https://pypi.org/project/fastapi/); [FastAPI release notes](https://fastapi.tiangolo.com/release-notes/)). It now requires Pydantic v2, having dropped v1 support in stages through 0.128 ([FastAPI migration guide](https://fastapi.tiangolo.com/how-to/migrate-from-pydantic-v1-to-pydantic-v2/)). Its foundation, Starlette, reached 1.x ([PyPI starlette](https://pypi.org/project/starlette/)). Sebastián Ramírez's company **FastAPI Labs raised a Sequoia-led seed round** to build FastAPI Cloud, so FastAPI now has a commercial backer, as Laravel does ([Sequoia](https://sequoiacap.com/article/partnering-with-fastapi-labs-simplified-app-deployment)). The practical rule is to **pin FastAPI to an exact version** and read release notes on every upgrade. **Flask 3.1** is mature, slow-moving and widely deployed, worth reading and maintaining but not a first framework. Litestar (2.25) and Quart (the async Flask) are credible niches ([PyPI flask](https://pypi.org/project/Flask/); [PyPI litestar](https://pypi.org/project/litestar/); [PyPI quart](https://pypi.org/project/quart/)).

### SQLAlchemy 2.1, Pydantic v2 and Celery form the shared substrate

Outside Django, the data layer is **SQLAlchemy 2.1** (typed `Mapped[]` models and `select()`), with **Alembic 1.20** for migrations and **psycopg 3.3 or asyncpg 0.32** for PostgreSQL ([PyPI SQLAlchemy](https://pypi.org/project/SQLAlchemy/); [PyPI alembic](https://pypi.org/project/alembic/); [PyPI psycopg](https://pypi.org/project/psycopg/); [PyPI asyncpg](https://pypi.org/project/asyncpg/)). SQLModel, the FastAPI author's blend of SQLAlchemy and Pydantic, is convenient, but at **0.0.50 it is still signalling an unstable API** ([PyPI sqlmodel](https://pypi.org/project/sqlmodel/)). **Pydantic 2.14** is the validation layer that ties the ecosystem together, used across FastAPI, Django Ninja, SQLModel and the LLM SDKs. Pydantic v1 does not run on Python 3.14+ ([PyPI pydantic](https://pypi.org/project/pydantic/)).

For background work, **Celery 5.7 with Redis** remains the default in job ads and legacy code. RQ reached 3.0, Dramatiq, arq and Taskiq offer lighter or async-native options, and **Temporal's Python SDK (1.36)** covers durable, long-running workflows ([PyPI celery](https://pypi.org/project/celery/); [PyPI rq](https://pypi.org/project/rq/); [PyPI taskiq](https://pypi.org/project/taskiq/); [PyPI temporalio](https://pypi.org/project/temporalio/)). Real-time work runs on Django Channels or Starlette WebSockets. Server-rendered interactivity increasingly uses HTMX with django-htmx and Django 6.0's partials, Python's counterpart to Laravel Livewire and Blazor static SSR ([PyPI django-htmx](https://pypi.org/project/django-htmx/)).

## The data and AI branch is Python's moat and its job engine

No other backend ecosystem has a neighbouring branch this large. **pandas 3.0 (January 2026) made Copy-on-Write and a real string dtype the defaults.** It has breaking changes, and the pandas team advises upgrading via 2.3 ([pandas 3.0](https://pandas.pydata.org/community/blog/pandas-3.0.html)). **Polars 2.x** made its streaming engine the default for lazy queries ([Polars 2.0 upgrade guide](https://docs.pola.rs/releases/upgrade/2/)). Machine learning runs on NumPy 2.5, scikit-learn 1.9, **PyTorch 2.15** and Hugging Face **transformers 5.x**. Data engineering runs on **Airflow 3.4**, Dagster, Prefect 3 and Ray ([PyPI torch](https://pypi.org/project/torch/); [PyPI transformers](https://pypi.org/project/transformers/); [PyPI apache-airflow](https://pypi.org/project/apache-airflow/); [PyPI ray](https://pypi.org/project/ray/)). The LLM application layer is the closest to backend work: the **Anthropic and OpenAI SDKs, LangChain 1.x, LlamaIndex and the MCP Python SDK 2.x**, almost always served through FastAPI ([PyPI anthropic](https://pypi.org/project/anthropic/); [PyPI openai](https://pypi.org/project/openai/); [PyPI langchain](https://pypi.org/project/langchain/); [PyPI mcp](https://pypi.org/project/mcp/)). GitHub reports that **nearly half of new AI projects are mainly Python** ([GitHub Octoverse 2025](https://github.blog/news-insights/octoverse/octoverse-a-new-developer-joins-github-every-second-as-ai-leads-typescript-to-1/)).

The branch shapes the backend job market directly. **UK FastAPI ads mention AI in 56.1% of cases and LLMs in 30.5%**, and FastAPI ads rose from 143 to 239 in a year, overtaking Django's 206 ([ITJobsWatch FastAPI](https://www.itjobswatch.co.uk/jobs/uk/fastapi.do); [ITJobsWatch Django](https://www.itjobswatch.co.uk/jobs/uk/django.do)). PyTorch ads rose from 156 to 209, with a median up 10% to £82,500 ([ITJobsWatch PyTorch](https://www.itjobswatch.co.uk/jobs/uk/pytorch.do)). The useful distinction is between three branches. AI application engineering (LLM APIs, retrieval, tools, evaluation) is a short step from FastAPI backend work. Classical ML (PyTorch, maths) and data engineering (Polars, Airflow) are separate careers that need their own depth. A backend learner can take the first branch without committing to the other two.

## Running Python in production means processes, pools and patience with the database

The 2026 server landscape has settled into two models. **Sync WSGI apps** (Django, Flask) run under Gunicorn's sync or gthread workers, roughly one process per core. **Async ASGI apps** (FastAPI, Starlette, async Django) run under Uvicorn, Granian or Gunicorn. Gunicorn changed most: after a two-year gap it shipped seven releases in 2026. **Gunicorn 24 introduced a native ASGI worker, stable since 25.1 in February 2026**, and HTTP/2 arrived in 25.0. The eventlet worker was removed, and 27.0 (November 2026) added HTTP/2 flood limits and stricter `Transfer-Encoding` handling ([Gunicorn news](https://gunicorn.org/news/)). Gunicorn is again a single process manager for both models, but its ASGI path is young. FastAPI's own guidance is blunter: on Kubernetes, run **"a single Uvicorn process per container"** and let the orchestrator replicate. `uvicorn --workers` suits a single VM, and the old `uvicorn-gunicorn-fastapi` image is deprecated ([FastAPI server workers](https://fastapi.tiangolo.com/deployment/server-workers/); [Docker Hub](https://hub.docker.com/r/tiangolo/uvicorn-gunicorn-fastapi)). **Granian**, a Rust server, is an active alternative ([PyPI granian](https://pypi.org/project/granian/)). Its speed claims come from its own 2024 benchmark, and it warns that libraries relying on asyncio internals can break ([Granian benchmarks](https://github.com/emmett-framework/granian/blob/master/benchmarks/vs.md); [Granian README](https://raw.githubusercontent.com/emmett-framework/granian/master/README.md)).

Packaging has a clear 2026 norm: **a multi-stage Docker build with uv**. The locked dependencies install first in a cached layer (`uv sync --locked --no-install-project`), then the project, and only the virtualenv is copied into a slim runtime image ([uv Docker guide](https://docs-next.astral.sh/uv/guides/integration/docker); [Hynek Schlawack](https://hynek.me/articles/docker-uv/)). Deployment targets span a VPS with systemd, Nginx and Gunicorn; containers on Kubernetes, Cloud Run, Render or Fly; and AWS Lambda through Powertools' event handler or the Mangum ASGI adapter ([Powertools](https://docs.aws.amazon.com/powertools/python/latest/core/event_handler/api_gateway/); [Render](https://render.com/articles/fastapi-production-deployment-best-practices)). Unlike .NET's `PublishContainer`, Python has no first-party image builder, so the Dockerfile is part of the craft. Migrations follow the same discipline as other stacks. Use backward-compatible expand-then-contract changes, and run `manage.py migrate` or `alembic upgrade head` as one pre-deploy job rather than in every replica. One Django trap is that its transactional migrations clash with `CREATE INDEX CONCURRENTLY` under PgBouncer's transaction pooling ([ClickHouse Django guide](https://clickhouse.com/docs/products/managed-postgres/guides/django)).

Scaling is mostly about connections and queries, not Python's speed. **Django 5.1+ ships native psycopg connection pooling, but one pool per process**, and `CONN_MAX_AGE` must be 0 when it is on ([Django databases](https://docs.djangoproject.com/en/stable/ref/databases/)). Replicas × processes × pool size must stay under Postgres `max_connections`, so many-pod deployments still need PgBouncer in transaction mode, with server-side cursors disabled ([Django databases](https://docs.djangoproject.com/en/stable/ref/databases/); [PgBouncer FAQ](https://pgbouncer.org/faq.html)). PHP's worker-mode runtimes hit the same wall. The baseline for observability is OpenTelemetry's zero-code agent, `opentelemetry-instrument`, which monkey-patches installed libraries ([OpenTelemetry Python](https://opentelemetry.io/docs/zero-code/python/)), plus Sentry, Prometheus and py-spy for live profiling. Benchmarks need the usual caution. FastAPI's docs claim a place "among the fastest Python frameworks" in TechEmpower and admit that raw Starlette and Uvicorn are faster ([FastAPI benchmarks](https://fastapi.tiangolo.com/benchmarks/)). Compiled stacks lead those synthetic tests by a wide margin, and real endpoints are dominated by database I/O.

The large case studies teach that Python scales organisationally if you pay for it. **Instagram runs "one of the world's largest deployments" of Django** on Meta's Cinder runtime fork ([Engineering at Meta](https://engineering.fb.com/2022/05/02/open-source/cinder-jits-instagram/)). **Dropbox type-checked about 4 million lines with mypy** ([Dropbox](https://dropbox.tech/application/our-journey-to-type-checking-4-million-lines-of-python)), migrated over a million lines from Python 2 to 3 incrementally ([Dropbox](https://dropbox.tech/application/incrementally-migrating-over-one-million-lines-of-code-from-python-2-to-python-3)), and moved performance-critical backends to Go ([Go case study](https://go.googlesource.com/website/+/237d41d9236bfaaabc9e42386a0816ae3b0e620d/_content/solutions/dropbox.md)). These stories date from 2016–2022, but the lesson holds. Typing, tooling and selective native rewrites keep Python viable at scale, and rewrites should follow profiling rather than fashion.

Python's ad count rose 44% year on year while its share fell from 8.43% to 5.24%, because ITJobsWatch's total pool roughly doubled to about 123,000 ads, a figure C#'s numbers confirm. The pay spread is wide: Python's 10th percentile is £43,750 and its 90th is £110,000 ([ITJobsWatch Python](https://www.itjobswatch.co.uk/jobs/uk/python.do)). Part of Python's premium over C# and PHP likely reflects senior data, ML and quant roles in the mix rather than higher pay for identical backend work.

The co-skill list is the most useful guide for a learner. **UK Python ads pair it with AI (38.7%), SQL (33.4%), AWS (32.6%), Azure (30.9%), CI/CD (29.5%), ML (18.0%), Terraform (16.4%), Kubernetes (15.1%) and Docker (14.5%)**, while "Degree" appears in only 17.2% ([ITJobsWatch Python](https://www.itjobswatch.co.uk/jobs/uk/python.do)). Employers hire for Python plus data, cloud and delivery skills, and treat the framework as secondary. Globally, Python is used by 57.9% of developers. Among Python users, data analysis (about 48%) and web development (about 46%) are near level, with ML at 41% ([Stack Overflow 2025](https://survey.stackoverflow.co/2025/technology); [The Register](https://www.theregister.com/software/2025/08/19/python-usage-growing-while-foundation-struggles-for-funds/937983)).

The entry rung is Python's distinctive weakness. **71.8% of people learning to code use Python**, more than any other language ([Stack Overflow 2025](https://survey.stackoverflow.co/2025/technology)). **Half of Python developers have two years or less of professional experience** ([JetBrains survey 2024](https://lp.jetbrains.com/python-developers-survey-2024/)), against 16% for .NET. Entry-level hiring is down across the industry. Stanford's ADP analysis finds US developers aged 22–25 down almost a fifth since late 2022, and its authors call the finding descriptive, not causal ([The New Stack](https://thenewstack.io/ai-junior-developer-hiring/)). Counter-signals exist, such as IBM reportedly tripling entry-level hiring ([same](https://thenewstack.io/ai-junior-developer-hiring/)). The safe reading is that a Python junior competes in the most crowded queue and needs a deployed, tested portfolio with SQL, Docker and one cloud to stand out. Freelance rates vary by platform: Upwork benchmarks $20–45/hour, and Lemon.io quotes mid-level at $64–85/hour and senior at $89–112/hour, though the same page contradicts itself on senior minimums ([Upwork](https://www.upwork.com/freelance-jobs/us/python/); [Lemon.io](https://lemon.io/hire-python-developers/)). Python Institute certifications (PCEP, PCAP) are cheap, and career sites describe them as helpful early but "not a strict requirement" ([Dice](https://www.dice.com/career-advice/are-python-certifications-worth-it-in-2025-what-you-need-to-know)). With AWS and Azure in about a third of ads, a cloud associate certification is probably the stronger tie-breaker.

### The staged path from zero to scalable systems

No authoritative Python curriculum or learning order exists, and no data measures how long each stage takes. The sequence below synthesises the official tutorial structure, current library version floors and UK co-skill data. **The durations are estimates for 10–20 hours of study a week, not sourced figures.** Each stage ends in a portfolio artefact, because in this market the artefact matters more than a certificate.

| Stage | Focus | Prove it with |
|---|---|---|
| **1. Modern Python foundations** (about 0–3 months) | Python 3.14/3.15 installed with uv (`uv python install`, `uv init`, `uv run`). Types, strings and f-strings, control flow, functions, comprehensions, built-in collections, exceptions, files and UTF-8. Modules, packages and `pyproject.toml`. Classes, dataclasses, enums, iterators, generators, context managers and decorators. Type hints in PEP 695 style, checked by pyright or mypy. First pytest tests, Ruff and Git. Skip pre-2023 tutorials built on TypeVar boilerplate, `setup.py` or Python 2 habits. | An automation CLI (Typer or argparse) that parses CSV or Excel files and emails a report, with tests and type checks |
| **2. Django, SQL and the web** (about 3–8 months) | HTTP, SQL fundamentals and PostgreSQL. Django 6.x: models, migrations, the ORM (`select_related`, fetch modes), auth, admin, forms, templates with HTMX partials, CSP. An API layer with DRF or Django Ninja. Pydantic v2. pytest-django and coverage. | A deployed Django app with auth, roles, CRUD on Postgres and a documented API: junior-employable |
| **3. Professional API engineering** (about 8–15 months) | FastAPI with dependency injection, OpenAPI, async and `TaskGroup`. SQLAlchemy 2.1, Alembic, psycopg 3 or asyncpg. Hypothesis and integration tests. Multi-stage uv Dockerfiles, a GitHub Actions pipeline (`uv sync --locked`, Ruff, type check, pytest, pip-audit), pre-commit. Supply-chain hygiene: locks, hashes, Trusted Publishing. Celery with Redis, then arq or Taskiq. Structured logging. | A FastAPI service with background jobs, containerised, with green CI and published coverage: looks mid-level |
| **4. Production operation and cloud** (about 1–2 years) | Gunicorn or Uvicorn worker models, Nginx, systemd. One cloud (AWS or Azure) with Terraform. Kubernetes or Cloud Run, readiness probes, graceful shutdown. Django native pooling and PgBouncer, connection maths, Redis caching, rate limiting. Expand/contract migrations as pre-deploy jobs. OpenTelemetry, Sentry, Prometheus multiprocess mode, py-spy. Channels or WebSockets, RabbitMQ or Kafka clients. Architecture patterns from *Architecture Patterns with Python*: repository, unit of work, events. | The stage 3 system split into services with messaging and traces, deployed with IaC, released without downtime |
| **5. Scale, internals and specialism** (2+ years) | Horizontal scaling, read replicas, queue-depth autoscaling. Locust or k6 load tests on real endpoints. Python internals: data model, GIL versus free-threading, subinterpreters, GC, Tachyon profiling, Rust extensions with PyO3. Temporal for durable workflows. A specialism chosen by market: AI application engineering (LLM SDKs, MCP, retrieval, evaluation harnesses), data engineering (Polars, Airflow or Dagster), ML serving (PyTorch behind FastAPI), or platform work. | A load-tested production system with SLO dashboards and a written bottleneck and cost report, or an LLM service with an evaluation suite |

The resources are strong and largely free through stage 3. For stage 1, the [official tutorial](https://docs.python.org/3/tutorial/), [CS50P](https://cs50.harvard.edu/python/) and [Exercism's Python track](https://exercism.org/tracks/python) all serve well. So does ***Automate the Boring Stuff*, 3rd edition (No Starch, 2025)**, free to read online and now with database chapters ([No Starch](https://nostarch.com/automate-boring-stuff-python-3rd-edition); [automatetheboringstuff.com](https://www.automatetheboringstuff.com)). For stage 2, use the [official Django tutorial](https://docs.djangoproject.com/en/stable/intro/tutorial01/) and the [Django Girls tutorial](https://tutorial.djangogirls.org). For stage 3, use the [FastAPI tutorial](https://fastapi.tiangolo.com/tutorial/) and the [uv Docker guide](https://docs-next.astral.sh/uv/guides/integration/docker). For stages 4–5, ***Effective Python*, 3rd edition (125 items, through Python 3.13)** ([Pearson](https://www.pearson.com/en-us/subject-catalog/p/effective-python-125-specific-ways-to-write-better-python/P200000010820)), *Fluent Python* 2nd edition ([O'Reilly](https://www.oreilly.com/library/view/fluent-python-2nd/9781492056348/)) and the free [*Architecture Patterns with Python*](https://www.cosmicpython.com) are the standard texts. One warning: ***Two Scoops of Django*'s newest edition targets Django 3.x (about 2020)**, so it is useful for patterns but dated on specifics ([Django Forum](https://forum.djangoproject.com/t/book-two-scoops-of-django-3-x/3251)).

## Python against PHP and .NET for the same learner

The three ecosystems now ship on near-identical rhythms. Python 3.15 arrived on 9 October 2026, .NET 11 on 10 November and PHP 8.6 on 19 November ([devguide](https://devguide.python.org/versions/); [Announcing .NET 11](https://devblogs.microsoft.com/dotnet/?p=61205); [php.net](https://www.php.net/releases/8.6/en.php)). All three have funded flagship frameworks, security-aware package managers and the same thin entry rung. They differ in how much the platform decides for you, what the market rewards, and where each can take a career.

| Dimension | Python (late 2026) | PHP (late 2026) | .NET (late 2026) |
|---|---|---|---|
| Release and support | Annual October minors; 5 years each; 3.15 newest, 3.12 practical floor | Annual minors; 2 years active + 2 security; 8.6 newest, 8.4 floor | Annual majors; LTS 3 years, STS 2; .NET 10 LTS and 11 STS both to Nov 2028 |
| Type system | Gradual, optional hints with generics (PEP 695), enforced by external checkers | Gradual typing, no native generics; PHPStan fills the gap | Static, compiler-enforced, generics, nullable references, C# 15 unions |
| Dominant web stack | Split: Django 6.x (product/full-stack) and FastAPI 0.x (APIs/AI), Flask legacy | Laravel 13 on Symfony components | ASP.NET Core with EF Core 10 |
| Toolchain ownership | Community and vendor: uv/Ruff (now OpenAI-owned), pytest, mypy/pyright | Community: Composer, PHPStan, Pest | First-party: SDK, analyzers, OpenAPI, container builds, Aspire |
| Runtime model | Long-running processes; GIL means scale by processes; free-threading optional | Shared-nothing FPM by default; worker mode optional | Long-running Kestrel, true multithreading, Native AOT option |
| Raw performance | Slowest of the three on CPU; hot paths moved to Rust/C | Middle; JIT barely helps web workloads | Fastest; performance is a yearly product feature |
| Adjacent branches | Data, ML, AI apps, automation, scientific computing | WordPress, Drupal, e-commerce | Desktop, Unity games, Azure, AI services |
| UK perm ads (6 months to Nov 2026) | 6,461, median £71,991 | 470, median £50,000 | C# 3,356, median £62,500 |
| Global usage (SO 2025) | 57.9%; FastAPI 14.8%, Flask 14.4%, Django 12.6% | 18.9%; Laravel 8.9% | 27.8%; ASP.NET Core 19.7% |
| Share of learners using it (SO 2025) | 71.8% | 14.5% | 23.1% |
| Learning curve | Gentlest first month; difficulty arrives with async, packaging and deployment | Gentle; output in a browser in minutes | Steepest first month (types, async, DI), least to unlearn later |

Sources: [Stack Overflow 2025](https://survey.stackoverflow.co/2025/technology); [ITJobsWatch Python](https://www.itjobswatch.co.uk/jobs/uk/python.do); [ITJobsWatch PHP](https://www.itjobswatch.co.uk/jobs/uk/php.do); [ITJobsWatch C#](https://www.itjobswatch.co.uk/jobs/uk/csharp.do); [php.net supported versions](https://www.php.net/supported-versions.php); [.NET support policy](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core).

Four differences matter most for a learner aiming at scalable systems. First, **Python has the widest market and the most crowded entrance**. It has nearly twice C#'s UK ads and fourteen times PHP's, but half its practitioners have two years or less of experience, against 16% in .NET. A Python junior needs the strongest portfolio of the three to stand out. Second, **Python's demand is the least web-shaped**. A .NET or PHP learner who masters ASP.NET Core or Laravel matches most of their ads. A Python learner who masters only Django matches a small minority, because AI, SQL and cloud dominate the co-skills. Third, **Python asks the learner to assemble the production stack**. .NET ships container builds, telemetry, resilience and orchestration as one documented platform. Python's equivalent is uv, Gunicorn or Uvicorn, a hand-written Dockerfile, OpenTelemetry's agent and Celery, all excellent but chosen separately, and its key framework is still pre-1.0. Fourth, **Python's ceiling is broader rather than faster**. It cannot match .NET on raw throughput, and it lacks PHP's cheap-hosting and CMS economy. But it is the only one of the three where a backend developer can move into AI application, data or ML work without changing language.

The choice follows from the learner's goal. Choose **Python** for the largest job pool, the AI and data branches, or a gentle first month followed by deliberate depth. Choose **.NET** for salaried enterprise and Azure work, the most integrated production platform, or performance-sensitive systems. Choose **PHP** for freelance web work, fast first results, or the WordPress and e-commerce economy. The stage 5 skills (stateless scaling, connection pooling, expand/contract migrations, OpenTelemetry and load-tested releases) transfer almost unchanged between all three.

## Conclusion

The research overturns the usual reason for choosing Python. Its ease is real, but in 2026 it is a liability as much as an asset: the easiest language to start is also the one where most learners start, so "knows Python" separates almost no one. What separates candidates is visible in the job data and largely absent from beginner material: SQL, a cloud, CI/CD, containers and increasingly AI integration, layered onto typed, tested code. The strategy that follows is to treat Python as the entry ticket and the deployed system as the product. Pull stage 3 habits, such as locked dependencies, CI, Docker and a running service, into the first six months. Pick the AI-application branch early if the goal is employability, because that is where FastAPI demand is growing fastest.

Three shifts will redefine Python mastery before Django 6.2 LTS and Python 3.16 arrive in 2027. The first is whether free-threading becomes the default build, which would turn thread safety from an expert concern into a baseline skill, much as worker mode is doing for PHP. The second is how OpenAI stewards uv and Ruff, now that the de facto toolchain of the world's most-used language belongs to an AI company. The third is whether FastAPI reaches a stable 1.0 or keeps shipping breaking changes as the AI economy's default web layer. The data leaves several things uncertain. The 2026 PSF and Stack Overflow results were not yet available, uv's current adoption share is unmeasured, and the true split between backend and data/AI hiring within Python ads can only be inferred from co-skills.
